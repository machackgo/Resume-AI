# Stage 4C-0 professional curriculum contract

This stage designs and audits data. It does not train, optimize adapters, replace model weights, alter frozen retrieval, or regenerate historical releases. The contract is versioned `stage4c0-v1`; the research basis is `stage4c0-research-v1`. Acceptance criteria and the task vocabulary are set before the pilot. Implementation defects may be repaired with recorded revisions and fresh hashes; a failing pilot cannot justify weaker truth or professional-quality gates.

The requested teacher configuration is `gpt-6-astra` with `ultra` reasoning. The current orchestration does not independently expose its backend identity. Observed model, observed reasoning, provider token usage and monetary cost remain `null` unless actually returned. These fields must never be inferred from the requested configuration. Wall-clock runtime can be measured independently. The code and immutable request bytes can be reproduced; a stochastic teacher response is not promised to regenerate bit for bit.

## Research and design boundary

The research snapshot contains 30 attributed public sources and 65 original principles across job analysis, resumes, technical resumes, ATS parsing, letters, application answers, outreach, truthfulness, current conventions and accessibility. Every task maps to exact principle IDs in `contracts/task_principles.v1.json`; `contracts/research_linkage.v1.json` resolves each ID to its version and source IDs. `TRUTH05` governs the whole dataset. The source register retains scope, access limitations and copyright restrictions. Public sample resumes, personal records and copied job postings are not training content.

The design applies these distinctions:

- ATS parsing is a vendor-specific extraction concern, separate from recruiter relevance and accessibility (`ATS01`–`ATS06`, `ACC03`–`ACC04`). There is no universal ATS score or pass guarantee.
- Good bullets identify the actual contribution, task and supported result or purpose (`RES02`, `TECH01`). A number is optional. Ownership verbs, technology identity, chronology and same-event metrics are factual constraints (`RES03`, `RES07`, `TECH03`, `TECH05`, `TECH07`).
- Selection and whole-document coherence matter as well as individual sentence polish (`RES01`, `RES09`, `RES11`, `CL02`). The curriculum therefore includes complete resumes and letters, not only isolated rewrites.
- Required qualifications, preferred qualifications, responsibilities, eligibility and employment conditions remain distinct (`JOB01`–`JOB08`). Exact alternatives and thresholds survive normalization.
- Personal preferences and sensitive factual answers require supplied user decisions or trusted facts (`APP02`, `APP05`, `APP07`, `APP08`). Job terms cannot establish willingness or eligibility.
- Company, motivation and outreach relationship claims require actual context (`CL04`, `OUT01`, `OUT03`). Generic flattery cannot replace grounded personalization.

A typical concise US industry resume is the default context. It is not a universal international or academic-CV rule. Employer requirements override generic conventions (`CONV02`). Current federal page limits are time-sensitive, destination-specific context rather than a global rule (`RES05`, `ATS06`). Binary rendering, tagged-document reading order, parser behavior and assistive-technology checks belong to the future File Generator; structured-content acceptance does not certify them (`ACC04`).

## Stable task vocabulary

The ten tasks deliberately separate analysis, evidence mapping, content selection and final composition. Section variants use one task with an enum instead of multiplying near-identical tasks.

| Task | Output responsibility | Distinctive quality check |
|---|---|---|
| `ANALYZE_JOB` | Source-spanned job atoms, modality, logic groups, numeric constraints and ambiguities | Required/preferred, AND/OR, eligibility and work conditions preserved |
| `MAP_JOB_TO_CANDIDATE` | Requirement-level evidence labels, supported claims and specific gaps | Missing/adjacent evidence is `UNKNOWN`; partial conjunction is `PARTIALLY_SUPPORTED`; explicit contradiction is `UNSUPPORTED` |
| `GENERATE_RESUME` | Coherent header and ordered semantic sections | Every identity/date/skill and narrative leaf grounded; selection and whole-document consistency |
| `GENERATE_COVER_LETTER` | Salutation, a few connected paragraphs, closing and signature | Relevant examples complement the resume; no invented motivation or company fact |
| `ANSWER_APPLICATION_QUESTION` | Routed factual, behavioral, motivation, preference or eligibility answer | Exact answer or actionable user-input request; exact limit respected |
| `IDENTIFY_MISSING_INFORMATION` | Specific missing fields, reason codes and answerable questions | Material gaps distinguished from harmless optional omissions |
| `DRAFT_OUTREACH` | Purpose-appropriate subject/body/salutation/closing | Actual relationship/context and one proportionate request |
| `SELECT_RESUME_CONTENT` | Prioritized evidence/event selections, omissions and section order | Strong relevant evidence selected within space constraints |
| `REWRITE_BULLET_FOR_JOB` | One same-event, job-relevant claim | Stronger prose without stronger facts |
| `GENERATE_RESUME_SECTION` | One typed section | Correct structure and grounded section-specific content |

The section enum is `SUMMARY`, `SKILLS`, `EXPERIENCE`, `PROJECTS`, `EDUCATION`, `CERTIFICATIONS`. A generic summary may be omitted. Student projects may be foregrounded without being promoted to employment. Sections have conventional semantic heading constants and preserve order explicitly. Experience, project, education and certification entries carry an `event_id`, separate title/organization/date/location claims and grounded bullets; project origin is explicit.

## Public input and hidden evaluator boundary

`contracts/visible_input.schema.json` defines the exact public input. Every object rejects unknown keys. Its only top-level fields are `schema_version`, `task`, `job`, `profile`, `rag`, `request`, `constraints`.

`job` contains the job ID, original synthetic text, and source-quoted requirement IDs. `ANALYZE_JOB` may receive an empty requirement list so it performs the extraction itself. Source spans in outputs are zero-based Unicode character offsets into the exact job text; the end is exclusive and the quote must equal that slice. The numeric atom representation preserves its text value, unit and comparison without converting an ambiguous phrase into an invented precision. Any normalized requirement list used by other tasks is visible task context, not a candidate-answer oracle.

`profile` contains a candidate ID and explicit facts `{fact_id,event_id,field,value,provenance}`. Values are strings representing the exact renderable source value. Provenance is one of `CANDIDATE_ASSERTED`, `EXTERNAL_OBSERVED`, `AUTHENTICATED`; these states must not be conflated. Opaque fact IDs are public so final claims can cite them. The hidden evaluator adds candidate ownership, event predicates, expected contradictions and other checks in a separate scenario/oracle object. Those additions never enter teacher, critic or student messages.

`rag` preserves the agreed frozen evidence projection: evidence/event/source IDs, `content`, source type and origin, `trust: "untrusted_data"`, verification policy `resolve_supports`, exact citation handle and separately scoped authenticated attestations. Each content string is at most 640 characters. There are at most five distinct exact-text groups, with multiple source-provenance entries allowed for a group. A citation span covers `[0,len(content)]`. Retrieval membership, similar wording and a legitimate handle do not establish entailment. An authenticated attestation identifies its own source, exact fact IDs and `exact_fact_ids_only` policy; it is never a global trusted-content toggle. Stage 3J retrieval parameters remain untouched.

`request` declares the instruction, section or question, question type, explicit word/character limits, channel/purpose and source bullet. Irrelevant fields are null. `constraints` carries locale, as-of date, excluded fact IDs and required sections. Prompt builders must construct this allowlisted object; deleting one known `oracle` field from an arbitrary scenario is insufficient isolation.

The teacher receives only the public input, task schema, relevant original research principles, rubric, writing instructions and declared budget. The critic receives the same public context, proposed output, canonical hashes and a deterministic inventory of auditable leaves. It does not receive teacher hidden reasoning, hidden oracle fields or sealed test answers. A fresh critic context prevents simple self-approval; a second call to the same requested model does not establish independent model-family judgment and must not be described as such.

## Output and factual coverage

All outputs use `{schema_version,task,status,artifact,trace}`. Each task has its own strict schema. `COMPLETE` selects the task artifact. `USER_INPUT_REQUIRED` selects a blocked artifact containing specific missing-information questions and `partial_artifact: null`. Material uncertainty is visible and actionable. Optional irrelevant facts can be omitted without blocking useful work.

Candidate-facing text is represented as `{text,evidence_ids,fact_ids}`. This covers names, organizations, titles, dates, location, skills, credentials, paragraphs, salutations and signatures as well as bullets. A wrapper can contain a compound sentence, so its independent review must identify every factual predicate within it. Empty references are allowed structurally for pure courtesy or nonfactual text, but only a fresh critic's `NONFACTUAL` review can admit them. A generic candidate ability assertion is factual even if it contains no proper nouns or numbers. A greeting naming a person is also factual.

Facts may be supported by exact profile IDs, RAG evidence IDs or both. Citations alone cannot override contradiction, wrong-event support, wrong-candidate ownership, excluded facts or a different technology/action. Structured identity/date fields must match appropriate profile values exactly. Legitimate job facts use source spans and must remain separate from candidate predicates. A job requirement never supplies a candidate skill.

The trace is a compact public decision record: selected requirements, selected/excluded evidence, applicable principle IDs and bounded decision codes with reference IDs. It contains no private chain-of-thought, unbounded rationale or confidence score. Claims may not be hidden in trace or free metadata. The deterministic inspector traverses actual output content; it does not trust a teacher-produced checklist of claims.

`iter_claims` finds all claim wrappers. `iter_audit_leaves` inventories every substantive string under the artifact, including project origin and factual content outside wrappers. Structural enums, constant headings and reference IDs are excluded from semantic leaf review because they have separate schema/reference checks. Every remaining leaf receives exactly one hash-bound review. Job source quotes, gap questions and short field descriptions may be reviewed as job facts or nonfactual questions, as appropriate. The independent critic atomizes substantive factual clauses so a correctly cited number cannot conceal an unsupported action or entity in the same sentence.

## Frozen acceptance and professional rubric

`contracts/acceptance_gates.v1.json` and `contracts/rubric.v1.json` define acceptance before the pilot. The eight dimensions are grounding, task completion, job relevance, specificity, writing, structure/coherence, uncertainty handling and downstream usability. Scores use anchored integers 0–4.

Grounding must equal 4. Every other dimension must be at least 3 and their unweighted mean must be at least 3.5. A score of 3 means professional and usable with only optional minor edits; 4 means specific, concise, coherent and ready for content publication. A material factual defect fails regardless of the mean. A genuinely inapplicable dimension is recorded explicitly in a brief public assessment; reviewers cannot drop dimensions selectively.

Acceptance additionally requires strict schemas, valid source references, correct exact fields, deterministic numeric/technology/action/entity/scope checks, correct source spans, all stated constraints, no unresolved issues and complete critic coverage. Every factual atom must be `SUPPORTED`; unknown, partially supported or contradicted candidate prose is rejected or revised. Correct uncertainty labels inside mappings are allowed and evaluated for correctness. The critic must return `ACCEPT` with no unresolved revision requests. Its input hash, complete output hash, each leaf path and each UTF-8 text hash must match the exact current artifact. A passing report cannot be replayed after any modification.

Deterministic extraction is a conservative error detector, not a universal entailment proof. Its job is to catch independent numeric, technology, action-strength, entity, exact-profile and scope violations without relying on teacher annotations. The semantic critic closes gaps such as implied ownership, unsupported broad capabilities and omitted predicates. Hidden synthetic ground truth can expose event/ownership/contradiction errors unavailable from lexical overlap. Disagreement or unresolved support fails closed. High-scoring prose cannot erase a hard failure, and an oracle does not license information absent from the public input.

The factory stores immutable requests, complete raw responses, parsed artifacts, deterministic checks, critic responses and revision outcomes. Each accepted row has all version/hashes necessary to inspect its lineage. A maximum of two revisions means one original attempt plus up to two corrected attempts, each with fresh independent review and hashes. Invalid JSON is a failure, not silently repaired into a target. Exhausted or irreparable failures remain rejected with their reasons. No external communication or application submission is performed.

## Token budget and complete-artifact realism

The existing local `models/Qwen3.8-27B` tokenizer/model identity is retained; no substitution is authorized. Stage 4B's 4,608-token figure was a forward/backward tensor-length demonstration. Complete optimization examples reached 4,233 tokens. The provisional ceiling here is therefore 4,233 tokens for the complete serialized future student conversation, pending the required CPU tokenizer measurement. This is a conservative design bound, not a new measured feasibility claim.

Teacher-generation context may include the larger full rubric and schemas; future student messages use their own frozen compact system contract and visible task input. Both serializations must be distinguishable in logs. The student token budget is measured using the actual local Qwen tokenizer and exact intended chat template, including role/control tokens and full assistant target. Reports retain input, assistant and total token counts, tokenizer/template fingerprints and per-task distributions. No guessed tokens, character-to-token proxies or truncation qualify.

Full resumes contain a header, relevant ordered sections and substantive background, with enough detail to be recognizably complete for the scoped synthetic candidate. They cannot be relabeled complete after truncation. If a record exceeds the bound, select a coherent smaller relevant evidence context or narrower original scenario, regenerate a complete artifact and rerun all checks. Do not silently remove the end of an artifact or discard difficult tasks to meet a length statistic. The pilot must measure complete resumes and letters before scale is claimed.

## Seed pool, coverage and splits

The professional task mixture is provisional: 10% job analysis, 12% mapping, 18% full resumes, 10% letters, 16% application answers, 10% missing-information identification, 6% outreach, 6% selection, 7% bullet rewriting and 5% section generation. This is a target within the new professional pool, not a claim about final row counts. A future separately authorized training plan may combine 70% professional data with 30% immutable Stage 4A truthfulness replay. This stage performs no training and never supplies historical test targets to professional teachers.

Start from a finite original seed pool with measured coverage. Expand in response to documented missing task/section/difficulty coverage or observed failures, not a promised row count. Report attempted, rejected and accepted examples separately. Pilot attempt acceptance is descriptive, not a gate that can be met by hiding failed attempts or weakening criteria. Straightforward, selection/synthesis and ambiguity/conflict/adversarial scenarios tentatively receive 30/40/30 proportions. Complete artifacts, qualitative accomplishments, technical near misses, exact metrics, source trust, eligibility, preferences, limits and outreach relationships all require coverage.

Split before generation by connected scenario family. Candidate, event, job-template, paraphrase, counterfactual and derived-task lineages are edges in one grouping graph. Every connected component belongs wholly to one split. Nominal train/validation/test proportions are 80/10/10; a small pool uses a preregistered explicit assignment so holdouts exist without claiming precise generalization estimates. The split salt and assignments are frozen and recorded. Near-duplicate text and token-shingle audits can merge components and require a prerelease resplit; they must never separate related variants to improve apparent task balance. Test references remain sealed from train teachers and tuning. Evaluation requests may use their own visible test inputs without revealing expected answers.

## Catastrophic regression suite

`contracts/catastrophic_regressions.v1.json` defines 24 failure/control cases before the pilot. They cover number/event transfer, action escalation, technology identity, exact entity/date fields, tenure, provenance promotion, RAG injection, missing versus negative evidence, partial conjunctions, logical alternatives, sensitive/preference inference, course-to-production promotion, fabricated contacts/referrals, false grounding annotations, stale hash replay, omitted factual leaves, keyword stuffing, visible conflicts, explicit limits/truncation, excluded or altered profile facts and oracle/split leakage. Positive controls cover grounded qualitative impact and exact authenticated scope so the system cannot pass simply by rejecting everything.

Release requires zero accepted catastrophic truth failures, zero cross-split family overlap, zero protected historical changes and zero false accepts on the deterministic regression suite. All ten tasks and all six section variants must appear in the coverage report, and a full resume must pass an end-to-end coherence and budget check. If the finite accepted seed pool misses required coverage, report the shortfall and expand or revise the pool; do not certify a complete curriculum. Historical replay outputs are redirected to Stage 4C-0 audit paths and remain separate from teacher input. Protection manifests, historical tests, token measurements, teacher/critic evidence and accepted-data checksums all contribute to the final go/no-go report.

## Python integration

`stage4c0/contracts.py` uses only the standard library. It exports `TASKS`, `SECTIONS`, `TASK_PRINCIPLES`, `INPUT_SCHEMA`, `OUTPUT_SCHEMAS`, `CRITIC_SCHEMA`, `RUBRIC`, `ACCEPTANCE_GATES`, `CURRICULUM`, `TEACHER_SYSTEM`, `CRITIC_SYSTEM` and `REVISION_SYSTEM`.

The validator helpers are `validate_schema(value,schema)`, `validate_input(value)`, `validate_output(output,task=None)` and `validate_critic(critic,visible,output)`. They return error lists; an empty list means only the checks that helper implements passed. It does not certify hidden semantic claims. `canonical_hash` hashes canonical UTF-8 JSON with sorted keys, compact separators and nonfinite numbers forbidden. `text_hash` hashes the raw UTF-8 string. `iter_claims` yields `(object_pointer,claim)` and `iter_audit_leaves` yields `(text_pointer,text)`. JSON pointers escape `~` and `/` normally.

`python3 -m stage4c0.contracts --root .` materializes the JSON contracts, three versioned prompts and a content-hash manifest without producing candidates or training artifacts. The manifest hashes the research snapshot, generated contract files and generator code. Final execution provenance must preserve the actual frozen bytes used by every request even if later code repairs receive a new manifest.

## Pre-pilot implementation hardening and additive rubrics

Initial code inspection found systemic validator defects before any accepted release: pooled citation text could transfer metrics across events; hidden technology/number tags could supply facts absent from public input; evidence-only references could bypass excluded fact IDs; empty exact fields could avoid equality checks; title values were not constrained to compatible source fields; verification wording trusted a provenance label without exact attestation; entity checks were missing; and `NONFACTUAL` could bypass scrutiny for generic ability assertions. These are implementation findings, not teacher-quality failures. The hardened validator binds entry scope, uses public support text for factual allowances, requires appropriate exact fields and attestations, checks named entities and source spans, and restricts empty-reference courtesy text. Independent critic atoms also cannot use job-only spans to establish candidate facts or cite another entry event. All accepted artifacts must rerun the current validator; earlier clean-looking reports do not bypass it.

The positive-only support filter also rejected truthful denials grounded in explicit negative evidence. Its repair accepts a faithful explicit denial or narrow single-clause negative answer, while retaining independent semantic review and rejecting affirmative reuse of the same negative technology/action tokens. The old and new focused test suites pass 52 tests, including accepted qualitative/same-event examples, distinct complete-event sentences, valid exact attestations and safe courtesy. These tests establish the named checks, not exhaustive semantic soundness.

Ten explicit task rubric artifacts were added under `contracts/task_rubrics/`, including `job_analysis_rubric_v1.json`, `candidate_mapping_rubric_v1.json` and `resume_rubric_v1.json`. Each retains the common frozen gates, adds task-specific professional anchors and resolves exact principle/source IDs. `contracts/task_rubric_supplement.v1.json` records their hashes and the original pilot manifest hash. Existing pilot requests already contained the common rubric and relevant task principles; their bytes are not retroactively replaced. Thresholds did not change. The original generator hash remains historical provenance for those pilot contracts; the final implementation freeze must separately record the repaired source-code hashes.

A generic oracle expectation of `COMPLETE` is not an unconditional truth for every composition task. If a specifically requested section requires an exact missing identity field, `USER_INPUT_REQUIRED` can satisfy the public schema and be justified by independent critique. In a full resume, an absent optional section should normally be omitted instead of blocking the complete artifact. Deterministic expected-status checks belong to cases with explicit factual/decision prerequisites, while the critic assesses materiality and unnecessary blocking for generative artifacts. This policy applies to the task class, not to a particular model response.

## Factory integrity audit before release

The current focused suite passes 95 tests: 60 grounding/schema-helper checks and 35 pipeline/provenance checks. Mock outputs and mock critic reports used in these tests are isolated unit-test scaffolding, never accepted curriculum data or evidence of professional quality. The audit did not inspect actual teacher or critic target files.

A discovered traversal defect treated the `GENERATE_RESUME_SECTION` artifact's `section` object as an enum and skipped its nested semantic leaves. The helper now skips only non-object structural values; a regression requires full traversal. Any critique issued with the incomplete inventory must be regenerated in a new immutable request location. Conservative false positives also treated leading grammatical prepositions as part of an organization name and rejected comma signoffs or multiple individually nonfactual courtesy sentences. Repairs strip only the specified grammatical prefixes and recognize a bounded sequence of individually checked courtesy sentences; invented names, factual adjuncts, prior relationships and quantified expertise remain rejection controls. Profile references and RAG references are a support union, so an independently supplied identity can accompany RAG-grounded contribution text without a fictitious identity-to-RAG link. Explicit negative evidence is scoped to each denial sentence and cannot authorize a later affirmative reuse of its technology/action.

Complete saved-dataset validation now requires actual token measurement, historical exclusion and a four-file provenance bundle for each example: `request.json`, `teacher.json`, `critic_request.json`, `critic.json`. A structural preflight is explicitly labeled as non-release work. The validator recomputes canonical hashes, checks exact public input and artifact equality, verifies current prompt/rubric/schema/research bytes, and requires the critic wrapper's independently recorded `critic_request_sha256`. It checks the corrected complete leaf inventory as part of the critic request. The request allowlist rejects hidden oracle fields and unregistered overrides. A missing original binding cannot be manufactured by a curator.

Factory audits retain raw response file hashes and count malformed teacher/critic responses as rejected attempts without aborting the rest of the batch or rewriting raw files. Accepted rows record their generation run and exact critic-request directory. Revisions require correctly bound original requests, outputs, critique requests, critique wrappers and audit hashes; their counters must be nonboolean integers in the frozen range. Task mappings require actual supporting references and claims; selection checks evidence-only references as well as fact IDs. Split checks include both declared family lineage and actual candidate/job identities. Historical empty inventories fail closed, and token counts must agree with sequence lengths and include a nonempty assistant target.

These checks establish record and evaluation integrity. They do not certify an independently observed teacher backend, universal semantic entailment, or real vector retrieval. The frozen RAG context uses canonical origin values and support-scoped verification objects that differ from the professional view. A separate versioned compatibility projection and CPU test against the real frozen helpers must establish round-trip source/identity/span/scope behavior before compatibility is claimed. Alias mappings and fact-to-claim/support mappings must be retained explicitly. Synthetic resolver/helper tests must be labeled simulation; no retrieval execution is implied.

## Additive teacher routing clarification and inventory ordering

The factory now prepares `teacher.v2` requests by default. Its additive prompt explicitly states the already enforced product rules: UNKNOWN mapping rows contain no supporting evidence/fact IDs or supported claims, and material missing application facts/preferences route to `USER_INPUT_REQUIRED`, including on the missing-information task. Adjacent true evidence can be recorded as an omission instead of being mislabeled as support. The original v1 wording established the semantic labels but left these serialization/status conventions ambiguous. This is a systemic prompt-contract clarification; it does not change source facts, research principles, quality thresholds, schemas or student message serialization.

`contracts/prompts/teacher.v1.txt`, its original manifest and all existing requests/reviews remain intact. `contracts/prompts/teacher.v2.txt` and `contracts/teacher_routing_supplement.v2.json` record the new exact bytes and linkage. `prepare(..., teacher_prompt_version="teacher.v1")` or CLI `--teacher-prompt-version teacher.v1` remains available. V1 requests revise under `revision.v1`; v2 requests revise under `revision.v2`. Provenance validation permits only the exact registered base/revision templates and checks the revision counter. A fresh three-scenario rerun can therefore test the two mapping cases and the missing-information case under v2 with unchanged authored ground truth, separately from repairing the original v1 attempts.

Provenance inventory validation also now compares unique path-bound entries rather than their list order. JSON object-key order changes when assistant messages are canonicalized; array positions remain meaningful and are encoded in JSON pointers. Nine pilot inventory failures were exact matches by path, text and text hash with only a traversal-order difference. The saved critic-request hash still binds its original ordered bytes. Duplicate or omitted paths, altered text/hash and changed array positions remain failures. This repair requires no new critique for an inventory that already covered the same exact leaves; the earlier missing-section-object defect still requires a new complete critique.

The explicit-module focused suite now passes 104 tests, including registered prompt defaults, unchanged v1 bytes, revision lineage, unknown-version rejection and inventory-order invariance. Test fixtures remain separate from teacher data.
