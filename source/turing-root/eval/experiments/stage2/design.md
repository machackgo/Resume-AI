# Stage 2 pre-implementation design

Baseline protected: results/baseline/base-v1-2325384-eval3. Dataset, schema, scorer and base prompt verified byte-for-byte against baseline config before new code. The control manifest hashes all existing eval and baseline artifacts; Stage 2 adds files, never changes those files. Keep model weights/path, NF4 double quantization, BF16, seed 42, thinking=false, greedy decoding, max_new_tokens=1536 fixed.

Failure taxonomy: (1) Markdown JSON fences invalidate the raw output contract, (2) unknown/tentative evidence leaks into skills, (3) compound and partial claim labels are inconsistent, (4) citation IDs give false confidence when prose adds an activity/outcome not present in evidence. Exact citation sets also sometimes penalize defensible negative evidence, and safe subclaims can cite unsafe compound IDs.

Schema ambiguities documented, not changed: skills has no proficiency/support field; atomic claim decomposition is absent; bullets reference proposed claims and evidence without explicit alignment per clause; negative citations vs no-support citations are ambiguous; partial familiarity vs skill proficiency has no threshold field; schema permits semantically duplicate IDs and arbitrary strings. Keep all gold labels and deterministic metrics unchanged. Do not optimize citation wording to specific gold exceptions. The unchanged scorer cannot verify prose entailment, so a separate qualitative audit is required.

Strategy: one versioned system contract plus task instruction and JSON-serialized candidate evidence, job, request, proposed claims, vocabulary, and unchanged schema sections. No case IDs or gold labels appear in messages. Generic rules only, no answer examples, no answer-specific numbers or claims. Skills require recorded experience or training; bullets are limited to fully supported claim IDs and evidence-entailing clauses. Classification can recognize exact arithmetic entailment; generation preserves explicitly stated quantities, addressing the user's stricter no-new-metrics contract without relabeling baseline gold.

Installed Transformers generation source exposes prefix_allowed_tokens_fn and LogitsProcessorList, but no response_format/json_schema entrypoint. Outlines, xgrammar and lm-format-enforcer are absent. Token filtering would require a new grammar implementation/integration. Start with the simpler explicit JSON instruction; no constraints or assistant prefill yet. No dependencies installed. If smoke fails, diagnose before a versioned revision.

Development protocol: one new synthetic smoke case with a different domain and vocabulary, tested outside the eight scored benchmark cases; inspect raw output; freeze prompt and smoke provenance; then one full benchmark run with no prompt changes based on full-run failures. Smoke checks format, safe skills, compound partial support, unknown evidence, unsupported metrics, and minimal grounded bullets. It is a development probe, not held-out evidence of generalization.

Additional promotion metrics are supplementary only. Existing score.py and definitions remain untouched. Compute the same supplementary metrics for both baseline and Stage 2; distinguish strict parse availability from recovered baseline diagnostics. A formatting failure never counts as a successful zero-promotion result. Gold match/claim label promotions and skill-list promotion proxies are reported separately, with denominators and coverage.
